# MaaXuexi 开源项目对比与扩展建议

核查日期：2026-10-17，北京时间。依据公开源码、默认分支提交及 GitHub Issues；没有执行外部项目安装包，也没有将 README 分值当作本机实测。多个同源 fork 合并看待。

## 建议结论

继续使用现有 MaaXuexi，优先完善视频内容选择与真实核分，再增加订阅。没有找到一个经过当前 App、相同账号与 MuMu 环境实测、能证明替换后更稳或更少验证的完整开源方案。

## 额外积分途径

|候选|当前证据|实施优先级|
|---|---|---|
|订阅|本机今天积分页明确有每日上限2分。旧源码有去重、分类遍历与核分的实现。|最高。优先待订阅，每批2个后核分；没满再检查上新。建议最多3批，满分立刻停止，没有可用候选就报告，不为凑分大量订阅。|
|本地频道|旧项目能做，当前这一轮尚未确认对应计分卡片。|次选。先识别当前可计分入口，再实测是否到账，不能直接承诺固定多1分。|
|专项/每周答题|历史项目支持，但旧上限和入口不能代表当前规则。|仅在当前账号存在未完成且可计分任务时接入，不把历史“61/63分”相加。|
|发表观点|本机任务页存在1分上限，需要对外发布内容。|保留本人撰写、发布的入口与核分，不默认生成或发送公共评论。|
|登录/签到|本机已有登录1/1。|已经覆盖，不能再包装成一个额外每日奖励。|
|广播/音频|当前视听规则把音频与视频归在同一12分上限。|可以研究节约串行等待时间，但不是额外积分来源，须实测播放启动、停止和积分归属。|
|分享、收藏、点赞、点点通、运动|老项目常把不同奖励、历史规则放在一起。|先确认当前积分规则；本人运动和学习活动可核分，不作为自动化凭空新增的分值。|

订阅应保存账号名称及本次点击结果，区分“按钮已变化”和“积分到账”。首次订阅候选是有限资源，不能保证永久每天都有2分。这里是可执行设计，订阅功能尚未安装，尚未声称已拿到2分。

## 稳定性与速度

1. 最有价值的是任务名定位、已完成跳过、动作后确认页面、最后核分。已有部分保持，不复制固定列表下标与大量无界重试。
2. 普通页面若能获得Android控件，优先使用控件定位；题目、WebView和缺失控件再用本地OCR。当前还没有相同环境的速度对照，不能声称换控件一定提速多少。
3. 每日题先严格匹配提示，模型只处理不能直接确定的题。本机08:42这组5题中4题走提示匹配，1题请求DeepSeek。结算页确实显示5题全对与+5分，但旧坐标记录异常中断自动返回，不能把那轮算作整轮成功。
4. 其他脚本的秒答经常来自OCR加旧题库哈希查找，不等于模型本身更快、更准。沿用用户不依赖旧题库的偏好，不加入过期题库作为默认答案来源。

## 网友反馈的边界

- [上游问题16](https://github.com/ravizhan/MaaXuexi/issues/16)报告视频识别后不断滑动、每日题失败；[问题12](https://github.com/ravizhan/MaaXuexi/issues/12)报告识别文章但不进入。说明同类问题也出现在上游，需要真实流程验收。
- [dundunnp问题597](https://github.com/dundunnp/auto_xuexiqiangguo/issues/597)报告广播、本地新闻、双人退出、订阅页面卡住，不能只按功能清单选择项目。
- [问题704](https://github.com/dundunnp/auto_xuexiqiangguo/issues/704)是旧版用户收到系统警告的个案。它能证明存在报告，不能推算当前封号率，也不能证明某个操作就是唯一原因。
- [问题742](https://github.com/dundunnp/auto_xuexiqiangguo/issues/742)记载过按星期轮换趣味模式的规则；当前程序应继续识别今日计分标记，不硬编码旧星期表。

没有找到能量化证明某个开源项目显著降低验证码、警告或封号概率的对照数据。更少的重复操作有助于减少无用请求，但不等于平台认可自动化，也不能宣传免封或完全无人值守。

你提到引流或对外使用，还需注意一个具体的来源问题：[上游README](https://github.com/ravizhan/MaaXuexi/blob/master/README.md)同时写有禁止商业用途、禁止倒卖和盈利，以及采用AGPLv3。这里仅记录原文表述，不自行判断它们的法律效力；产品化前需要查明授权关系，不能仅凭开源仓库公开就认定可直接销售。
